# Velomine v2: inter-club social layer

Status: idea, not committed. This is the place for features that connect **clubs to each
other**. They are deliberately outside v1: v1 has to make a single club work first.

The product values are in `values.md`. The rule for everything here is in its
"Inter-club social principles" section: **clubs are the nodes, not people.**

## Why this layer exists

Strava's social graph connects individuals: followers, kudos, public segments, leaderboards.
That graph creates pressure, cheating and eventually a paywall. Velomine should connect
clubs, and let members appear as aggregates unless they explicitly opt in.

The goals:

- give clubs a reason to talk to each other;
- make the platform more useful as a regional cycling community;
- create a growth loop where clubs invite clubs;
- do it without a global feed, ads or personal data leaving a club.

## Design principles

- Opt-in at both ends: one club publishes or invites, the other accepts; either can revoke.
- Aggregate by default: totals, averages, participation, not individual names.
- The club admin moderates its own club's participation.
- No global activity feed, no follower graph, no public individual leaderboards by default.
- Everything published is also exportable and deletable.
- Fair competition: normalise by club size or active members, or use divisions.
- No cheating economy: verified rides, e-bike/indoor filters, minimums, club self-policing.
- Works for cloud and self-hosted clubs without a central service we control.

## Feature ladder

| Layer | Feature | What moves between clubs | Why |
|-------|---------|--------------------------|-----|
| 1 | Club profile (opt-in public page) | Name, town, disciplines, size, contact, join code | Discovery; no member data |
| 2 | Friendly club link | Mutual invite code, later a signed key | Trust graph; revocable |
| 3 | Inter-club challenge | Aggregate totals only | The hook; zero personal data |
| 4 | Joint event / club ride | Event metadata, RSVP counts, attendance | Real-world socialising |
| 5 | Shared routes | GPX, attribution, difficulty | Clubs share good routes |
| 6 | Regional calendar | Public opt-in events, ICS feed | Find rides when travelling |
| 7 | Exchange ride | Event + join request | A visitor joins a friendly club's ride |

## First slice: friendly clubs + a monthly club challenge

1. A club publishes an opt-in profile and gets a friendly-club invite link.
2. Another club accepts; both admins can revoke.
3. One club creates a challenge: period, metric (distance, climbing, hours, rides,
   participation), outdoor/indoor/e-bike rules.
4. Each club computes its aggregate locally from ready rides only.
5. The host shows a leaderboard of clubs, not people.

Fairness rules:

- Default score is average per active member or participation rate, not total kilometres.
- Show total and per-rider views; let the creator choose divisions by club size.
- Active member = at least one eligible ride in the period.
- Exclude e-bike rides from analog challenges, indoor from outdoor, and rides below a
  minimum distance/time.
- Period boundaries use the club's local time zone.
- Duplicate or suspicious rides are excluded; club admins can remove a ride from the
  aggregate.
- Individual names only with explicit member opt-in; otherwise top riders stay anonymous.

## Joint events

- Host club creates an event: date, route, groups (A/B/C), capacity, meeting point.
- It invites friendly clubs; members RSVP through their own club.
- The host sees counts by club; names only with member consent.
- After the ride, uploaded files can be matched to the event, so attendance becomes data
  instead of a WhatsApp poll.
- The public event page is server-rendered HTML with a join code; guests do not need an
  account to see it.

## Architecture

**Phase A — opt-in club profile and directory.** Clubs on the same deployment already find
each other through opt-in nearby discovery. This layer connects clubs across deployments:
cloud and self-hosted clubs. A club can publish a public profile (name, town, disciplines,
size, contact, join code) to a federated directory. The directory holds only metadata, never member data, and a club can
withdraw at any time. This is the discovery layer; challenges and events still use direct
federation.

**Phase B — direct federation.** Each club generates an Ed25519 key pair. A friendly-club
invite carries the club id, its host and public key. Clubs exchange signed HTTPS requests
for event invitations and aggregate challenge results. Allowlist, rate limit, and retries
through a `deliveries` table processed by a hosted service, like notifications: no broker. The same mechanism serves cloud and self-hosted clubs.

**Phase C — open federation.** ActivityPub-style discovery, public club pages, regional
calendars. Do not start here.

**Self-hosted clubs behind NAT** fall back to:

- **Challenge code:** the host generates a code; each club admin enters its aggregate
  locally; the host page shows the leaderboard.
- **Hosted event page:** one club hosts the event page; guests join with a code. Only event
  metadata is public, never ride data.

## Data model sketch

The database has an `interclub` schema; every table carries the local `club_id`:

- `friendly_clubs` — club id, peer base URL, peer club id, public key, state, timestamps.
- `federation_keys` — club id, public key, private key reference.
- `shared_events` — host club, event metadata, visibility, join code.
- `event_participants` — event, club, member, consent, attendance.
- `challenges` — host club, period, metric, rules, divisions.
- `challenge_entries` — challenge, club, aggregate values, signature, submitted at.
- `deliveries` — outbound message, state, attempts, last error.

## What to avoid

- A cross-club activity feed; it becomes Strava within a year.
- Public individual leaderboards and KOM hunting.
- A central "Velomine network" account or relay we control.
- Building federation before two clubs actually ask for it.
- Forgetting small clubs: normalise or use divisions from day one.

## Open questions

- First feature: challenge (async, viral) or joint events (real-world, more coordination)?
- Scoring default: per active member, participation rate, or divisions by club size?
- Do we need a public club directory, or only invite links between known clubs?
- How much of this can live in the server-rendered HTML pages instead of the Flutter app?
- If a club leaves the provider or moves to its own server, what happens to its published
  events and challenge results?
